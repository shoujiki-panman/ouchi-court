# おうち裁判の保守手順

作成日: 2026-10-24（日本時間）。この文書とチェック用スクリプト、GitHub Actions のワークフローを用意した段階で、自動監視が稼働したことにはならない。既定ブランチへの反映と実行履歴を別途確認する。

## 日次: 公開ページと配布ファイルを確認

Node.js 24 で、リポジトリのルートから実行する。

```sh
node scripts/health-check.mjs
```

既定の対象は `https://ouchi-court.panman.workers.dev/`。ローカルの確認用サーバーを指定する場合は、origin とリクエストごとの制限時間（ミリ秒）を指定できる。

```sh
node scripts/health-check.mjs http://127.0.0.1:8787/ 8000
```

正常なら終了コード `0`、失敗なら `1`。JSON の `checks` にファイル別の HTTP ステータス、経過時間、失敗理由が出る。1 回あたりホームページと JavaScript 6 本、利用量記録の新モジュールが必要な版では追加 1 本の GET のみを行い、各リクエストは既定 8 秒で打ち切る。レスポンスは最大 512 KiB に制限し、本文をログへ出さない。

確認するファイルは `/`、`/app.js`、`/live.js`、`/names.js`、`/sfx.js`、`/punishments.js`、`/capture-worklet.js`。HTTP 200 だけでなく、Content-Type とアプリ固有の目印も確認する。Cloudflare の SPA fallback により、存在しない JS の代わりに HTML が返るケースも失敗として扱う。リダイレクトには追従しない。

取得した `live.js` に `import { LiveUsage } from "./live-usage.js";` がある版では、`/live-usage.js` の配布も確認する。旧版では要求しないため、デプロイ前後の両方を点検できる。これは既知の依存 1 本だけを認識する仕組みで、取得したコード中の任意の URL をたどるものではない。

このチェックは AI API、MCP、KV、マイク、ゲームの進行を呼び出さない。AI の従量料金を発生させず、利用者の会話・名前・認証情報も扱わない。通常の静的配信アクセス分は発生する。

**成功が保証するのは、指定した静的ファイルが配布されていることだけ。** JavaScript の実行、Gemini の接続、実際の音声再生、判決、利用規約への適合、原価、iPhone 上の動作は別の検証が必要。新しい必須モジュールを追加した際は、スクリプトの `PROBES` とテストの `paths` も更新する。

## GitHub Actions での日次実行

`.github/workflows/health.yml` は毎日 01:17 UTC（日本時間 10:17）に、この静的配信チェックを実行する。GitHub の混雑等で開始が遅れることがあるため、実行時刻の保証はない。ジョブ全体は最大 3 分で打ち切る。

定期実行には、ワークフローがリポジトリの既定ブランチに反映され、GitHub Actions と当該ワークフローが有効である必要がある。反映後は Actions の「Production static health」から手動実行もできる。導入確認では、成功した実行履歴と `static-delivery-only` の JSON 出力を確認する。

失敗は通常の GitHub Actions の失敗として記録される。通知の配信先と有無は GitHub の通知設定に従う。Issue の自動作成、他人へのメッセージ送信、デプロイは行わず、秘密情報も必要としない。JSON 出力には公開ファイルのパス、ステータス、所要時間、失敗理由のみが含まれ、応答本文は含めない。

この定期チェックが成功しても、音声接続や AI・MCP 連携が正常と確認できたことにはならない。

## 異常が出たとき

1. ネットワークの一時障害かを区別するため、一度だけ再実行する。繰り返し成功を待つループは作らない。
2. HTTP エラー、Content-Type、目印の不一致、タイムアウトを切り分け、直近のデプロイ差分を確認する。API キーや会話ログを共有資料に貼らない。
3. 差分から直せる場合は修正ブランチと回帰テストを作成する。本番変更はテストと変更内容を確認してから行う。
4. 静的チェックが通っても利用者から音声障害の報告がある場合は、端末・OS・ブラウザ・操作手順を確認し、架空の会話で再現する。

## 週次: ゲームと販売準備の点検

- `node --test tests/*.test.mjs` を実行する。既存の名前・席の区別、判決読み上げ、ライバル記録の分離、HTML エスケープに加え、新しいヘルスチェックの失敗検知も検証する。
- iPhone の実機で、マイク許可・拒否、再挑戦、別アプリへの切り替え、復帰、音声の割り込み、正常な閉廷を確認する。OS とブラウザの版、再現手順、期待結果と実際の結果、確認日を記録する。
- 利用量が採取できた成人による検証セッションで、1 回あたり原価と接続時間の分布を確認する。発言・音声・名前は原価表に保存しない。
- AI プロバイダーの年齢条件、データ取扱い、価格、モデル廃止予定の変更を一次情報で確認する。子ども向け利用条件の解決と実機検証は試験販売の開始条件。
- 販売仮説、問い合わせ、離脱・再利用の理由から次に直す問題を 1 件決める。未検証の学習効果を宣伝文に加えない。

## 変更ごとの自動テスト

`.github/workflows/checks.yml` は PR と `main` への push で Node のテストと Chromium 上の `seat.cjs`、`dom-escape.cjs`、`session-lifecycle.cjs` を実行する。Playwright は `1.64.1` に固定している。準備時の npm とブラウザのダウンロードにはネットワークが必要だが、テストはローカルの架空データを使い、アプリから外部 API への通信は遮断する。GitHub に反映されてから有効になる。API キーは不要で、本番デプロイや定期監視は行わない。Chromium で通ったことを iPhone 実機の確認として扱わない。

監視結果と実機確認結果は分けて記録する。失敗時は「何が失敗したか、利用者への影響、次の対応」を通知し、正常時の通知頻度は運用設定で調整する。
